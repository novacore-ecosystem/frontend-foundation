# Internationalization (i18n) Architecture

This document explains how `@novacore/frontend-foundation` implements shared internationalization: locale standards, translation resolution, resource organization, tenant overrides, error-code translation, and permission translation. It complements `docs/backend-contract-sync.md` (which tracks *where backend-mirrored contracts come from*) — this document is about the i18n *architecture itself*, most of which is frontend-owned.

## 1. Locale standard

Locales are BCP 47 language tags, typed as a closed union rather than a bare `string`:

```ts
type Locale = "en" | "vi" | "zh-CN";
```

`en` = English, `vi` = Vietnamese, `zh-CN` = Simplified Chinese. Chinese is explicitly `zh-CN`, not bare `zh` — a future `zh-TW`/`zh-HK` would be a *different* locale, not a casing variant, and the type must be able to distinguish them.

Everything locale-related lives in `src/i18n/locale`:

| Export | Purpose |
|---|---|
| `SUPPORTED_LOCALES` | `readonly ["en", "vi", "zh-CN"]` — the single source of truth application code should read supported locales from, never redeclare. |
| `Locale` | The type derived from `SUPPORTED_LOCALES`. |
| `DEFAULT_LOCALE` | `"en"` — the platform-wide fallback. Centralized here; never hard-code `"en"` as a fallback elsewhere. |
| `LOCALE_METADATA` / `getLocaleMetadata` | Display name, native name (`"Tiếng Việt"`, `"简体中文"`), and text direction per locale. |
| `getSupportedLocales()` | Metadata for every supported locale, in `SUPPORTED_LOCALES` order — enough for a framework adapter to render a locale selector without maintaining its own list. |
| `isSupportedLocale(value)` | Type guard: is `value` exactly one of the supported codes? |
| `normalizeLocale(value)` | Best-effort normalization of a locale-ish string (case/region/separator variations) to a `Locale`, or `null`. See its doc comment for the exact, deliberate rules — including why bare `"zh"` resolves to `"zh-CN"` but `"zh-TW"`/`"zh-HK"` do not. |
| `resolveLocale(value, fallback?)` | `normalizeLocale(value) ?? fallback` (default `DEFAULT_LOCALE`) — the boundary function. Use this wherever an external value (tenant bootstrap, `Accept-Language`, a saved user preference) enters the system, so application code never writes `locale as Locale`. |

### Backend locale support — a known discrepancy

The backend's `NovaCore.BuildingBlock.SharedKernel.Constants.LanguageCodeConstant` (`src/BuildingBlocks/BuildingBlock.SharedKernel/Constants/LanguageCodeConstant.cs`) currently supports only `["en", "vi"]` — **not** `zh-CN`. This matters for exactly one thing: backend-owned, dynamically-editable content gated by that constant (permission/permission-group display-name translations — see §8). It does **not** limit this package's own static UI/error/common terminology, which is entirely frontend-owned content with no backend storage dependency. All three locales are fully supported for that content today. If the backend adds `zh-CN` support later, no change is needed on the frontend side.

## 2. Translation resolution — framework-independent

The core primitive, unchanged in spirit from before this phase: `createTranslator(sources, options)` returns a bound `translate(key, values?, callOptions?)` function. It is a plain closure — no React context, no Vue composable, no Angular service, no framework dependency of any kind.

```ts
const translate = createTranslator(
  { application: TRANSLATION_RESOURCES },
  { locale: "vi", fallbackLocale: "en" },
);
translate("common.actions.save"); // "Lưu"
```

### Resolution priority (deterministic, in order)

```text
1. tenant override,    requested locale
2. application dict,   requested locale
3. fallback dict,      requested locale
4. tenant override,    fallbackLocale     (only if fallbackLocale is set and differs from the requested locale)
5. application dict,   fallbackLocale
6. fallback dict,      fallbackLocale
7. onMissingKey strategy ("key" by default — return the key itself; "empty"; a custom function; or throw if strict)
```

`fallbackLocale` is **opt-in** (`undefined` by default) — a translator created without it behaves exactly as it did before locale fallback existed, so this was an additive, non-breaking change to `createTranslator`. Pass `fallbackLocale: DEFAULT_LOCALE` (or import it) to get platform-standard behavior: an incomplete translation for a requested locale falls through to English rather than showing a raw key.

### Interpolation

`{{name}}`-style placeholders (configurable delimiters). A placeholder with no matching value is left untouched rather than silently emptied, so missing interpolation data stays visible during development:

```ts
translate("common.welcome", { name: "Tan" }); // "Welcome, Tan"
```

## 3. Translation keys vs. human-readable labels

**Never show a translation key or a technical identifier to a user.** `product.abc.dgr`, `errors.user.notFound`, `order:view` are internal identifiers for developers and this package's own plumbing — not UI text. The resolved *value* (`"Product"`, `"User not found"`, `"Orders"`) is what a screen renders.

Key convention used throughout this package's own resources: `<namespace>.<section>.<name>`, lowerCamelCase segments, e.g. `common.actions.save`, `errors.user.notFound`, `permissions.categories.order`. Namespaces are documented in §5.

### Type-safe keys without code generation

`TranslationKey` (`src/i18n/keys`) is a plain TypeScript recursive type (`DotPath<typeof en>`) derived directly from the English resource object — no code-generation step, no build tool. It's a union of every dot-path key this package's resources define, e.g. `"common.actions.save" | "errors.user.notFound" | ...`, giving autocomplete and typo-catching wherever it's used (`ErrorDefinition.messageKey`, permission category keys).

`Translator`'s own `key` parameter is deliberately typed as plain `string`, not `TranslationKey` — applications and tenants add their own keys beyond this baseline via the `application`/`tenant` dictionary layers, and constraining every call site to this package's key union would break that extension point. Use `TranslationKey` for your own code when you want compile-time safety against *this package's* baseline; pass any `string` when working with app-defined or tenant-defined keys.

## 4. Tenant override integration

`TenantBootstrap.translations` (`src/bootstrap`) already models the three-layer shape (`tenant`/`application`/`fallback`) `createTranslator` expects — see `createTranslatorFromBootstrap`, which builds a translator directly from a bootstrap payload:

```ts
const translate = createTranslatorFromBootstrap(bootstrap); // locale normalized, fallbackLocale defaults to DEFAULT_LOCALE
```

`resolveTenantLocale(bootstrap)` is the single normalization boundary for `TenantBootstrap.locale` (an unconstrained `string`, since bootstrap payloads may come from systems that don't validate against this platform's locale list) — call it once rather than casting `bootstrap.locale as Locale` at every use site; `createTranslatorFromBootstrap` already calls it internally.

`createTranslatorFromBootstrap` only resolves from `bootstrap.translations` — it does **not** automatically merge in this package's own `TRANSLATION_RESOURCES` (common/admin/error/etc. terminology). If you want both a tenant's bootstrap translations *and* the platform's shared terminology available through one translator, compose them yourself:

```ts
const translate = createTranslator(
  {
    tenant: bootstrap.translations?.tenant ? { [locale]: bootstrap.translations.tenant } : undefined,
    application: bootstrap.translations?.application ? { [locale]: bootstrap.translations.application } : undefined,
    fallback: TRANSLATION_RESOURCES, // platform terminology as the lowest-priority layer
  },
  { locale, fallbackLocale: DEFAULT_LOCALE },
);
```

This is left as an explicit composition rather than baked into `createTranslatorFromBootstrap`, so the merge semantics stay visible and predictable rather than "magic."

## 5. Translation resource organization

```text
src/i18n/resources/
├── en/
│   ├── common.ts       — cross-application actions, statuses, pagination, table states
│   ├── navigation.ts    — the handful of universal nav items (home, dashboard, settings, ...)
│   ├── admin.ts         — shared admin-UI entity nouns (Users, Orders, Warehouses, ...)
│   ├── auth.ts           — login-screen terminology
│   ├── validation.ts    — client-side form validation messages
│   ├── errors.ts         — human messages for a representative MessageCode subset (§7)
│   ├── permissions.ts    — permission category fallback labels (§8)
│   └── index.ts          — merges the above into `en`, the completeness baseline
├── vi/   (same file layout, satisfies typeof en per file)
├── zh-CN/ (same file layout, satisfies typeof en per file)
└── index.ts — TRANSLATION_RESOURCES: Record<Locale, typeof en>
```

One small file per namespace per locale, not one giant per-locale file — easy to review a single namespace's diff across locales, easy to find where a given key lives.

### Compile-time completeness (not just a runtime test)

Every locale's resource is declared `satisfies typeof en<Namespace>` per file (and the merged `vi`/`zhCN` objects `satisfies typeof en` overall). This means a missing key, an extra/orphaned key, or a wrong nesting shape in `vi`/`zh-CN` is a **TypeScript compile error**, not a silent runtime gap — `pnpm typecheck` alone catches translation drift. `tests/i18n/resources.test.ts` additionally runs a runtime completeness check (collects every dot-path key per locale and diffs the sets) as defense in depth and to make drift visible in test output, not just compiler output.

## 6. Domain boundary — what belongs in the foundation

| Owner | Owns |
|---|---|
| **This foundation** | `common.*`, `navigation.*`, `validation.*` (generic client-side form messages), a representative `errors.*` subset, `admin.*` (platform-wide entity nouns only), `permissions.*` (category-level fallback labels only) |
| **A future admin/domain UI package** | Domain-specific admin screen copy beyond the shared entity nouns above (e.g. a specific form's help text, a workflow's step labels) |
| **The backend, dynamically** | Individual permission/permission-group display names and descriptions (`PermissionDefinitionTranslation`, admin-editable — see §8) |
| **Applications** | Anything application-specific, via the `application`/`tenant` dictionary layers passed into `createTranslator` |

Do **not** grow this package into a dictionary for every domain's every message. If a key is specific to one application's one screen, it does not belong in `frontend-foundation`.

## 7. Error-code translation

`src/errors` builds error-message translation on top of `api/error`'s `MessageCode` (it does not redeclare the code enum — `errors/codes` just re-exports it internally):

```text
Backend MessageCode (api/error, mirrors BuildingBlock.Domain/Enums/MessageCode.cs)
        ↓
ErrorDefinition (errors/definitions) — code -> messageKey -> defaultMessage
        ↓
translateError(error, options) (errors/translation)
        ↓
human-readable message
```

```ts
translateError({ messageCode: MessageCode.UserNotFound, message: "User not found" }, { locale: "vi" });
// "Không tìm thấy người dùng"
```

### Fallback chain (never returns a raw key or code in production)

```text
1. ErrorDefinition found for the code?
   a. translate(messageKey) — tenant override, then platform translation, at the requested
      locale, then DEFAULT_LOCALE (createTranslator's fallbackLocale)
   b. ErrorDefinition.defaultMessage
2. No ErrorDefinition for the code (most domain-specific codes — see below):
   a. the backend-provided `message` string (English, not localized — used only because
      this package has no better answer for that code)
   b. a generic localized fallback ("errors.generic.fallback")
   c. `debug: true` -> the raw code, for developer tooling; otherwise a generic English sentence
```

### Why only a representative subset of `MessageCode` is translated

The backend's `MessageCode` catalog has ~90 members. `i18n/resources/*/errors.ts` translates every non-success numeric range in full (System, Validation, General Client, AuthN/AuthZ) plus one illustrative `notFound`-style code per business service (User, Product, Order, Inventory, Payment, Shipping) — about 20 codes, not all ~90. The remaining ~70 domain-specific codes (`ProductOutOfStock`, `CouponUsageLimitReached`, ...) are intentionally **not** translated here, for the same domain-boundary reason as §6: exhaustive per-domain error copy belongs to the application/domain package that actually raises that error, not this foundation. `translateError` degrades gracefully for any untranslated code via the fallback chain above — it never crashes or returns `undefined`.

## 8. Permission translation

Permission *identifiers* (`Permissions.Order.View` = `"order:view"`) must stay technical and stable — see `docs/backend-contract-sync.md`. Permission *display* must never show that raw identifier to a user.

**What this package provides:** `getPermissionCategoryTranslationKey(permission)` derives a category-level translation key from any permission (`"order:view"` → `"permissions.categories.order"`; `Permissions.Root`/`Permissions.User` → their own dedicated keys), and `translatePermissionCategory(permission, translate)` resolves it to a label ("Orders", "Đơn hàng", "订单") using a caller-supplied `Translator`.

**What this package deliberately does NOT provide:** a static translation of all 43 individual permission display names/descriptions. The backend already owns that content dynamically and lets admins edit it per language — `NovaCore.Auth.Domain.Entities.Permissions.PermissionDefinitionTranslation` (`src/Services/Auth/Auth.Domain/Entities/Permissions/PermissionDefinitionTranslation.cs`, one row per `(PermissionDefinition, LanguageCode)`, `DisplayName`/`Description` fields) and the parallel `PermissionGroupTranslation`. Hardcoding 43 × 3 static strings here would duplicate and fight that admin-editable backend content, not complement it. `PermissionDisplayInfo` (`src/authorization/translation`) documents the shape a future admin UI should expect when it fetches this dynamic data from the Auth service directly; `translatePermissionCategory` is the safe, always-available fallback until/unless that per-permission data is available for a given permission.

**Known backend gap:** because `LanguageCode.Create` (backend) only accepts `"en"`/`"vi"` (see §1), a `zh-CN` row cannot currently be stored in `PermissionDefinitionTranslation`/`PermissionGroupTranslation` even though this package's own category-level fallback labels fully support `zh-CN`. Reported in `docs/backend-contract-sync.md`, not silently worked around.

## 9. Framework adapter expectations

This package exposes only framework-independent contracts and functions. A future `@novacore/frontend-react` (or `-vue`, `-angular`) package is expected to build on top of, not duplicate:

```text
frontend-foundation
├── Locale, SUPPORTED_LOCALES, DEFAULT_LOCALE, LOCALE_METADATA, normalizeLocale/resolveLocale
├── TranslationKey, TRANSLATION_RESOURCES
├── createTranslator, TranslationSources, Translator
├── translateError, ERROR_DEFINITIONS
├── Permissions, hasPermission/hasAnyPermission/hasAllPermissions
├── getPermissionCategoryTranslationKey, translatePermissionCategory
        │
        ├──────────────┐
        ▼              ▼
   React adapter    Vue adapter    Angular adapter
   useTranslation()  composable    service
   useLocale()
   usePermission()
```

None of `useTranslation()`, `useLocale()`, `usePermission()`, a `TranslationProvider`, a Vue plugin, or an Angular provider exist in this package, and none should be added here — this phase is foundation-only.

## 10. Adding a new locale

Adding, say, `ja` (Japanese) should never require an architecture change:

1. Add `"ja"` to `SUPPORTED_LOCALES` in `src/i18n/locale/index.ts`, and its `LocaleMetadata` entry in `LOCALE_METADATA`.
2. Add a `src/i18n/resources/ja/` directory mirroring `en/`'s file layout (`common.ts`, `navigation.ts`, `admin.ts`, `auth.ts`, `validation.ts`, `errors.ts`, `permissions.ts`, `index.ts`), each `satisfies typeof en<Namespace>`.
3. Add `ja` to the `TRANSLATION_RESOURCES` map in `src/i18n/resources/index.ts`.
4. Run `pnpm typecheck` — any missing key surfaces immediately as a compile error, not a runtime surprise.
5. Run `pnpm test` — the completeness tests (`tests/i18n/resources.test.ts`) will also catch drift.
6. Update this document's locale table and `docs/backend-contract-sync.md` if the new locale interacts with any backend-owned, language-gated content (see §8).

## 11. Adding a new translation key

1. Decide which namespace it belongs to (§5/§6) — don't create a new namespace for one key.
2. Add it to the relevant `en/*.ts` file first — English is the completeness baseline.
3. Add the same key to `vi/*.ts` and `zh-CN/*.ts`. The `satisfies typeof en<Namespace>` constraint means the compiler will refuse to build until all three exist.
4. Run `pnpm typecheck && pnpm test`.
5. Reference it with the `TranslationKey` type where you control the call site (e.g. a new `ErrorDefinition`), for autocomplete and typo protection.

## 12. Handling missing translations

- **Default (`onMissingKey: "key"`)**: `translate()` returns the key itself. Visible to developers, non-fatal, safe default for this package's low-level `createTranslator`.
- **`translateError`** never does this — it always resolves to *some* human-readable text (see §7's fallback chain) or, in `debug` mode only, the raw error code. A normal (non-debug) user never sees a technical identifier from `translateError`.
- **`strict: true`** (on `createTranslator`) throws `TranslationMissingError` instead — useful for a build-time or CI check that every key an application actually calls exists, but not the production default.

## 13. Treating translation keys as a platform contract

A key such as `errors.user.notFound` should not casually be renamed to `errors.user.missing` — applications may already depend on it (directly, or indirectly via `ErrorDefinition.messageKey`). Prefer additive changes; document renames/removals as breaking changes with a version bump, the same discipline `docs/backend-contract-sync.md` applies to backend-mirrored contracts.
